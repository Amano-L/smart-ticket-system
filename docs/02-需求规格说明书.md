# 智能工单管理系统 - 需求规格说明书

## 1. 引言
### 1.1 目的
本文档定义智能工单管理系统的功能需求、非功能需求、接口需求和验收标准，作为设计、开发、测试和验收的依据。

### 1.2 范围
系统采用 Java 主后端 + Python Agent 辅助服务架构：
- Java 后端：认证授权、工单管理、状态流转、自动派单、审计日志、数据统计。
- Python Agent：工单自动分类、回复建议生成。
- AI 只做辅助，失败可降级，不影响工单主流程。

### 1.3 术语
| 术语    | 说明                                |
| :------ | :---------------------------------- |
| 工单    | 用户提交的问题、请求或投诉记录      |
| 状态机  | 工单状态流转规则，防止非法流转      |
| 派单    | 将工单分配给对应客服处理            |
| 降级    | AI 调用失败时，走规则分类或默认回复 |
| RBAC    | 基于角色的访问控制                  |
| traceId | 全链路追踪标识                      |

## 2. 总体描述
### 2.1 产品定位
轻量级智能工单管理系统，面向小团队客服场景，解决工单分类靠人工、派单效率低、状态不透明、重复回复多的问题。

### 2.2 用户角色
| 角色     | 编码       | 主要权限                                                     |
| :------- | :--------- | :----------------------------------------------------------- |
| 普通用户 | USER       | 创建工单、查看自己的工单、补充信息                           |
| 客服     | AGENT      | 查看分配给自己的工单、处理、回复、改状态、查看 AI 建议       |
| 客服主管 | SUPERVISOR | 查看所有工单、手动派单、查看统计                             |
| 管理员   | ADMIN      | 用户管理、角色管理、审计日志、系统配置、查看全部工单、查看统计 |

### 2.3 技术栈
- Java 21、Spring Boot 3、Spring Security、MyBatis-Plus、MySQL 8、Redis、Springdoc OpenAPI、JUnit 5 + Mockito
- Python 3.11、FastAPI、LangChain / LangGraph、大模型 API
- Docker Compose、Nginx

### 2.4 运行环境
- Java 21、Spring Boot 3
- MySQL 8、Redis
- Python 3.11、FastAPI
- Docker Compose
- 浏览器或 Postman 演示

### 2.5 设计约束
- 不做微服务、Kafka、K8s。
- 不做多租户、高并发。
- AI 不直接操作核心业务，只生成分类标签和回复建议。
- AI 调用超时 2 秒，失败必须降级。
- 核心业务必须有单元测试。

## 5. 用户故事与验收标准

### 5.1 用户创建工单
**用户故事**：作为普通用户，我希望提交工单后能自动分类和派单，以便快速得到处理。  
**验收标准**：
- 提交后工单状态为“待处理”。
- 系统自动分类，失败时走规则分类。
- 系统自动派单，记录派单日志。
- 返回工单编号和当前状态。

### 5.2 客服处理工单
**用户故事**：作为客服，我希望看到分配给我的工单和 AI 回复建议，以便提高处理效率。  
**验收标准**：
- 客服只能看到分配给自己的工单。
- 可查看工单详情和流转记录。
- 可查看 AI 回复建议，确认后发送。
- 状态流转符合状态机。

### 5.3 主管查看统计
**用户故事**：作为主管，我希望查看工单统计和客服工作量，以便调度。  
**验收标准**：
- 可查看工单数量、类型分布、平均处理时长。
- 可查看客服工作量。
- 数据与工单记录一致。

### 5.4 管理员查看审计
**用户故事**：作为管理员，我希望查看操作审计和 AI 调用记录，以便追踪问题。  
**验收标准**：
- 审计日志包含操作人、类型、时间、结果、traceId。
- AI 调用记录包含模型、耗时、结果、是否降级。
- 支持按工单、用户、时间查询。

## 6. 非功能需求
| 类型   | 编号     | 要求                                 |
| :----- | :------- | :----------------------------------- |
| 性能   | NFR-P-01 | 核心接口 P95 < 300ms（不含 AI 调用） |
| 性能   | NFR-P-02 | AI 调用超时 2 秒                     |
| 安全   | NFR-S-01 | JWT + RBAC，接口鉴权                 |
| 安全   | NFR-S-02 | 参数校验，防止 SQL 注入和 XSS        |
| 稳定   | NFR-R-01 | 统一异常、traceId、接口幂等          |
| 稳定   | NFR-R-02 | AI 故障不影响主流程                  |
| 稳定   | NFR-R-03 | 核心接口限流，防止突发流量           |
| 可维护 | NFR-M-01 | 分层架构、统一响应、日志规范         |
| 可测试 | NFR-T-01 | 核心 Service 单元测试覆盖率 ≥ 70%    |
| 可部署 | NFR-D-01 | Docker Compose 一键启动              |
| 可观测 | NFR-O-01 | 健康检查、日志、AI 调用统计          |

## 7. 数据需求
### 7.1 核心实体
- 用户、角色、用户角色关联
- 工单、工单流转记录
- 客服负载
- 审计日志、AI 调用记录

### 7.2 数据规则
- 工单编号唯一。
- 工单状态只能按状态机流转。
- 审计日志不可修改、不可删除。
- AI 调用记录保留模型、耗时、结果、是否降级。

## 8. 接口需求
- 使用 RESTful API，前缀 `/api`。
- 使用 Springdoc OpenAPI 生成文档。
- 统一响应格式：code、message、data、traceId。
- 统一异常码，详见《05-API设计》。
- 认证接口：登录、登出、当前用户。
- 工单接口：创建、列表、详情、编辑、状态流转、手动派单、客服回复。
- 统计接口：概览。
- 审计接口：查询审计日志。
- AI 接口：获取回复建议（Java 对外）。
- Java 通过 RestClient 调用 Python `/agent/classify` 和 `/agent/reply-suggest`。

## 9. 验收标准汇总
| 类别 | 标准                                                         |
| :--- | :----------------------------------------------------------- |
| 功能 | 登录、工单 CRUD、状态流转、派单、审计、统计全部可用          |
| 技术 | 13+ REST API、OpenAPI 完整、JWT + RBAC 生效、单测覆盖率 ≥ 70% |
| AI   | 50 条评测集准确率 ≥ 85%，超时 2 秒降级，AI 关闭后主流程可用  |
| 部署 | Docker Compose 一键启动，健康检查通过，traceId 可追踪        |

## 10. 风险与约束
| 风险          | 应对                                    |
| :------------ | :-------------------------------------- |
| AI 不稳定     | 超时降级、规则分类                      |
| 时间不足      | MoSCoW 砍功能                           |
| 范围蔓延      | 严格遵守“不做什么”                      |
| Java 深度不够 | 重点补 Spring、MySQL、Redis、事务、幂等 |
